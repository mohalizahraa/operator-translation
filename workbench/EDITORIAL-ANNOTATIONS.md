# In-manuscript questions and editorial annotations

**Status: founder-approved product direction (2026-10-26); implementation and migration not yet deployed.** This is the scoped project owner for question presentation, Google Docs comment attachment, and historical Questions-Doc retirement. [README.md](README.md) owns portfolio/status semantics; [SECURITY-AND-QUALITY-ROLLOUT.md](SECURITY-AND-QUALITY-ROLLOUT.md) owns source/revision, ledger, review, and recovery gates; [TRANSLATION-WORKFLOW.md](TRANSLATION-WORKFLOW.md) owns the book-processing sequence. This document does not relax Arabic-source or publication standards.

## Decision and user experience

**One persistent editable English Book per title.** Its manuscript text is the sole active English text target. Passage-specific editorial questions appear as **native Google Docs comments anchored to an exact English text range**, so a reviewer reads and replies at the relevant passage without switching documents.

The **existing Workbench D1 question ledger** retains durable and searchable question truth: stable `(project_id, question_key)`, canonical Arabic quotation, physical PDF source page and location, alternatives/proposed English, severity, reviewer answer, manuscript revision in which that answer was actually applied, and immutable activity. A Google comment is the **review interaction and location projection**, not an alternative source of truth for source coverage or an authorization to advance progress.

For broader editorial discussion without a precise passage, use a **Questions & Decisions tab inside the same English Google Doc**, if needed and after verifying final-export scoping. Do not append editorial questions to the book's publication text or create a separate Questions Doc by default. Neither comments nor side tabs count as translated source units, book footnotes, or TOC entries.

## Verified API substrate (scratch only, 2026-10-26)

Google Docs API `documents.batchUpdate` supports `insertComment: {content, range: {startIndex,endIndex,tabId}}`, `addCommentReply`, and `commentAction: RESOLVE`; use **UTF-16 Docs native ranges**, explicit tab identity, and a live revision guard. In a disposable scratch document the authenticated Google Docs connector:
- wrote two sample paragraphs;
- anchored one native comment to a selected phrase, and returned a comment ID, anchor ID, and quoted text;
- returned the same comment and quoted phrase on a subsequent comments read;
- accepted a thread reply and resolution; follow-up comment read returned `resolved: true`.

These operations verified the API and connected-account route, **not** rendered UI fidelity, mobile ergonomics, production Workbench integration, or preservation through structural rewrites. Google Drive `comments.create` with a custom anchor is **not** a substitute: on native Docs it may appear unanchored. Google Docs API support was announced generally available 2026-09-30; production use still requires a scratch full-cycle pilot with formatting, source-text, tab and rewrite edge cases. API documentation: https://developers.google.com/workspace/docs/api/how-tos/suggestions and https://developers.google.com/workspace/docs/release-notes .

### Repeatable native-index pilot — 2026-10-26

The latest `scripts/plan-native-comment-anchor.mjs` was run on a **second, disposable native Google Doc**, not a real book. After writing a small two-paragraph sample, the authenticated Docs API `get_document` returned its native text runs, revision and `t.0` tab. The structure planner selected the **exact unique 30-code-unit quote**, range `19..49`, and sent its `insertComment` request under `requiredRevisionId`. The reply returned the expected plain-text quote, new native `doco.` ID and `kix.` anchor. A separate `get_document_comments` readback returned the exact same quote and identifiers. `addCommentReply` plus `RESOLVE` succeeded, and readback reported the thread resolved with both replies. **The scratch Doc was deleted after verification**. No manuscript content, D1 question, review decision or translation progress was changed.

These checks prove that **authenticated, connector-driven, revision-guarded native comment operations work in a scratch document**. They do **not** prove that the public Cloudflare Workbench has Google OAuth, that public client-reported observations are authenticated, or that old `kix.` anchors can be recovered automatically after text revisions. Do not merge/deploy based on this isolated pilot alone.

### Historical-comment diagnostics

`scripts/audit-historical-native-comments.mjs` reconciles a live `get_document` readback with native comments readback **without writing anything**. It decodes quoted HTML entities, checks the indexed current English passage, and reports `unique_current_quote_candidate`, `ambiguous_current_quote`, `stale_or_reformatted_quote` or a manual blocker; an opaque native anchor ID plus a unique quote **still does not independently certify the precise anchor's current location**. Every classification keeps `arabic_source_page: null`, `question_decision_status: not_determined` and `safe_to_import_as_verified_question: false` unless actual source evidence is separately gathered. Book #118's seven existing native threads currently yield **five ambiguous quotes and two absent/reformatted quotes**. No duplicate comments were created.

`scripts/reconcile-english-targets.mjs` compares live Workbench project IDs against Drive's *existing* English Translation candidate titles/file identities without writing or exposing private document IDs in its report. It is deliberately read-only and does not authorize document creation/linkage from a filename or metadata-only permission check. Its 2026-10-26 run found **24 existing links, 152 restricted existing candidates, zero missing Docs, zero duplicate candidates and zero mismatched known IDs**. The browser UI now explicitly directs collaborators to *reuse* an existing Google Doc and no longer links to `docs.new`.

## Transaction and lifecycle contract

1. Resolve exact Workbench book ID, existing authoritative English Doc ID, Arabic PDF hash/physical page and target revision. Never infer the book from a title-only search or shift progress for an annotation.
2. Create or reuse the D1 `translation_questions` row with a stable key and preserved Arabic quote/source location **before** posting the comment. Draft a concise comment containing that key, source-page locator and targeted question. Preserve full context and alternatives in D1 even if Google comment content has a length cap.
3. Identify the **unique exact English text range** from native Google Docs structure; ambiguous, unavailable, or stale target text blocks auto-anchoring. The branch includes a pure `scripts/plan-native-comment-anchor.mjs` planner: its flattened `get_document_text` route refuses inconsistent paragraph indexes; for rich books with footnotes, the preferred `planNativeCommentAnchorFromStructure` consumes `get_document().tabs[].body` native `textRun` start/end indexes and refuses ambiguity, missing tabs, stale revisions, and unsupported structures. A read-only Book #118 live-structure trial located an exact 56-code-unit phrase in its manuscript while preserving a nearby footnote marker; **no comment or D1 row was created by that trial**. Do not attach a comment to the closest guess or another book. Guard insertion against concurrent edits by required revision and verify returned `commentId`, anchor/quoted text, Doc identity and location. Retry with readback and idempotent deduplication by stable key; never blindly insert duplicate comments after an uncertain response.
4. In the proposed branch, `translation_question_comments` and `GET/POST/PATCH /api/projects/:id/comment-links` preserve a durable idempotent D1 association between a source question and a native Docs comment. The POST stores exact comment/document/anchor/tab ID, original quote and creation revision, and rejects a wrong book, missing ledger question, or conflicting duplicate. The PATCH stores the caller's last observed `resolved`/`open` thread state and observed document revision without changing scholarly question status. Both use atomic activity and question-event history; the record is explicitly **`client_reported_unverified`** (self-declared by the public API client). This code is **not** deployed on the current site and does not itself create comments or authenticate Google. The authenticated Google Docs connector/agent must perform independent readback before any POST/PATCH, and public Workbench cannot safely claim always-on server-side sync or independently verified human review.
5. A human comment reply is **potential decision evidence**, not a D1 human-answer transition until the actual decision text/reviewer declaration is read, reconciled, recorded and confirmed. A resolved Google comment means the **thread** is resolved, not that its ruling was applied to the current English revision or that source fidelity is verified.
6. After applying an authorized answer, read back the changed English passage and perform the applicable Arabic fidelity, formatting, native structure and source-page checks. Only then record `applied_reference` to the exact target revision and update the D1 question state. New text revisions may invalidate prior anchors and QA/review evidence; investigate orphaned/reopened comments.
7. Before review/publication, reconcile **all** source-defined blocking questions, D1 answer/application states, native comment threads, and target revision. Unavailable comment access, divergent states, lost anchors, incomplete migration, or a missing final edition export remains an explicit OPEN gate. Do not auto-certify human review.

## Migration, compatibility and no-loss rules

- **On the new deployment**, the `PATCH /api/projects/:id/questions` `questions_doc_url` branch is read-only: an identical existing URL may return idempotently, while new/changed/cleared URLs return `409 legacy_questions_link_read_only`. The previous live site continues supporting its old link mutation until this PR is actually deployed; do not mistake a draft branch for production enforcement.
- **Freeze new separate-Questions-Doc creation now.** Preserve existing `projects.questions_doc_url` fields, linked Docs, and historical structured questions **read-only as legacy witnesses** until independently reconciled. The existing UI/API may still expose links while rollout is pending; don't silently clear them.
- Inventory old files and live D1 questions by stable project ID; verify matching English targets and **actual document contents**, including decisions, unresolved items, and context. Blank document titles alone are not proof a safe migration is complete.
- For each question or decision, upsert a stable D1 record with original provenance and historical status. Attach native comments only when uniquely anchored to a verified current manuscript passage. Inherited Docs comments can have short Drive-generated IDs rather than the newer `doco.` prefix, and their original text might not contain the subsequently assigned stable Workbench key; preserve their actual IDs and quotation rather than duplicating the thread. Initial comment state in D1 is `unknown` until a current connector readback is reconciled. Broad/missing-location issues can go to the same-document Questions & Decisions tab with stable keys, provided the tab is not part of the final English-book export.
- Verify new comment↔D1 state, actual current Doc, revisions, answers, permissions, and authoritativeness; preserve old files as archived witnesses until the founder explicitly authorizes cleanup. **No overwrite, deletion, mass status changes, fabricated approvals, duplicate Docs, or lost human judgments**.
- Roll out on one representative staging/scratch case through comment creation → read/reply → human decision capture → applied English revision → preserved note/footnote/TOC layout → detached-range recovery → export excluding editorial tab/comments → D1 readback; verify test outcomes, then expand to existing 22 discovered legacy Questions Docs. This is a migration inventory, not an assertion all 22 are complete or accessible.
- Existing original book statuses, verified physical-page checkpoint counters, and open/legacy QA gate **do not change** from adopting this design.

## Engineering acceptance and routing

New code must expose question stable key, linked comment ID/state and a measured unresolved count on resume/project screens **without requiring** `questions_doc_url`. Preserve existing D1 field/API compatibility until all consuming clients and historical links are migrated. Update Workbench frontend and fast-start hints, tests, help text, QA scripts, Operator translation profiles and deployment runbook only after source-of-truth boundaries are reconciled. A stale PR that makes separate Questions Docs obligatory must be retired, not merged.

**Pilot acceptance:** no wrong-book anchors or duplicate threads; exact quote/range returned and visible in Docs; reply/resolution works; human decision distinct from thread closure; orphaned/stale/conflicting revisions block rather than overwrite; existing old questions remain reconstructable; export publication artifacts contain no editorial text; live Workbench D1 and document states agree without translating or changing any page counters.
