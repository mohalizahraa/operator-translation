Status: user-approved execution plan, captured 2026-10-09. This project-owned file survives translation-projection synchronization. The current [Operator router](../AGENTS.md), [Arabic-book profile](../profiles/arabic-book-translation.md), and [Workbench contract](README.md) govern fidelity, formatting, access, progress, and publication. ## Source PDF line/page-index preflight for source-absence decisions (2026-11-16)

**Recovered failure:** An indexed PDF witness such as `L1354@P38` labels a **global extracted-text line** (`L1354`) and a **zero-based physical PDF page index** (`P38` → physical PDF page **39**). A previous translation QA pass mistakenly interpreted `L736` as physical source page 736/39 and, as a result, wrongfully removed a source-related paragraph and native footnote from Book #12. Those were restored. PDF page index and any **printed page number** are also distinct where front matter affects pagination.

Before a consequential assertion that source text, quotation or footnote is **absent**, before deleting source-related manuscript content, or before changing a citation on indexed-PDF evidence:

1. Identify the exact source PDF/edition and physical PDF page, and distinguish it from a printed page number or global text-extraction line ID.
2. For `Lnnn@Pxx` web/PDF-index witnesses, privately validate the page arithmetic using `node scripts/source-unit-overlap-preflight.mjs --check-pdf-page /private/pdf-page-witness.json`. The private JSON contains `{"sourceLocator":"L1354@P38","physicalPage":39,"sourcePageCount":486}`. An inconsistent `L736@P24` asserted as physical page 39 **must fail**.
3. Independently inspect the actual source page (prefer its rendered same-edition image), including **body and every source note**, check any page continuation, and compare it to the fresh native target revision before a bounded correction. If that proof cannot be recovered, classify the proposed deletion or citation change **BLOCKED** rather than inferring absence from garbled or partial text extraction.
4. Keep input witnesses, source-content excerpts, private Docs IDs and evidentiary decisions in the **private QA record** only. Never embed private source/manuscript text or IDs in a public GitHub issue, action log or test fixture. Preserve already written translation during uncertainty.

The CLI tests **coordinate consistency only**. A pass does not authenticate a PDF, prove an omission, authorize any deletion, establish semantic fidelity or credit an accepted source page. This applies alongside the existing one-writer/revision/idempotency preflight and every Arabic-translation assurance rule.

## Fail-closed source-unit idempotency before manuscript appends (2026-11-16)

**Verified incident:** In Book #12, a revision-guarded append duplicated Arabic physical source pp.37–40 that a designated writer had already translated in the live English target. The later duplicated block was removed with verified target readback; earlier work was preserved. A fresh revision check alone does **not** establish that a source unit is still untranslated.

Before **any** new English translation append, identify the correct Workbench project, exact source PDF/edition/hash and physical-page unit. Fetch the live target native Doc **again**, including complete existing source-to-target coverage, headings, notes, and tracked continuations. Build a PRIVATE manifest with the exact current target revision and **audited** existing unit IDs and physical page spans. Invoke `node scripts/source-unit-overlap-preflight.mjs /private/manifest.json /private/proposal.json` and require a PASS. Fail closed on stale revisions, unverifiable coverage, missing source hashes or any full/partial overlap: use a separately controlled, source-matched **amendment/reconciliation** to the existing unit instead of blindly appending. Retest immediately before commit, retain one designated writer, and verify the target again afterwards. The preflight validates the supplied manifest but **does not authenticate its provenance or fetch the actual Google Doc**; caller is responsible for that live evidence and its freshness. It does not establish source fidelity or accepted pages.

The run is evidence of attempted work, not evidence of accepted translation. Count duplicate recovery as `Rework` in the private Sessions ledger, preserving real timestamps and explicit lost time. Do not put private URLs, revisions, manuscript text or the private manifest into public GitHub, CI logs, or issues. This check is a necessary append precondition, **not a substitute** for independent source QA, native formatting, renderer review, rights/permissions or the founder's final-only website synchronization.

## Complete-source-once and PDF-native text reliability (2026-11-17)

**Quality-preserving throughput improvement:** Prefer one verified full original PDF per book over repeated four-page source requests when a valid private handoff exists. The Book #12 486-page canonical Arabic PDF was successfully recovered through the self-hosted source bridge after earlier four-page workflow failures. Validate original source SHA-256, true physical page count, edition identity and rendered page continuity before scheduling translation. Keep source bytes and page/footnote manifestations in a private, versioned workspace—not Git, public CI, issues, or an invented Workbench checkpoint. A one-day Actions artifact is a temporary transport, not durable storage; recover and verify its content before expiry.

**Never confuse digital text with readable source.** Some Arabic books use custom PDF font encoding: extracted pages may contain a surviving Qurʾānic quote surrounded by private-use characters, bidirectional-control floods, or mostly punctuation. The engine now flags obvious native-text corruption and blocks its connected translation route even if it finds an Arabic substring. This is a *fail-closed heuristic*, not proof that unflagged pages are complete. Inspect the actual rendered physical page and each original footnote; use source-checked transcription/OCR for damaged pages. Do not downgrade independent fidelity or the one-writer and revision/overlap gates to raise draft throughput.

**Measure the real critical path:** Source fetch/cache → native-text health and visual/OCR exceptions → coherent translation and source-note handling → first-pass native formatting → independent source-and-target review → rendered PDF/integration → human release and final-only website sync. Reuse already translated manuscripts and correct only bounded source-supported discrepancies. Continue deterministic independent preparation when source or reviewer access blocks a content step. Track true active time and independently accepted output by stage; add capacity only to a measured bottleneck without changing the $0 hosted-compute or single-GPU rules.

## Pipeline, not whole-book stage barriers

Prepare the active book once, then overlap source preparation/OCR for upcoming batches with translation of a source-checked batch. Do not require all OCR to finish before translation can begin. Whole-book extraction/OCR is allowed when measured startup costs make it cheaper and it does not delay the first usable batch or required review. Keep the ready queue bounded by downstream capacity; more busy machines are not automatically faster.

Actual translation content stays on one book at a time unless the user explicitly authorizes interleaving. Deterministic mechanical preparation may span books, as the current execution-substrate profile permits. Never trade source fidelity, complete text-surface coverage, or checkpoint verification for throughput.

## Native Google Docs bounded-batch fast path (2026-11-20)

**Purpose:** Reduce repetitive network edits and the confirmed inherited **1-point text-style defect** without lowering source, note, fidelity, or rendering gates. Use the single-writer `scripts/prepare-native-draft-batch.mjs` planner only for a fully source-identified logical unit. This is a private, optional fast path, not a separate translation engine or an independently accepted batch.

- **Preconditions:** Recover the exact original PDF/edition/hash and the rendered body and all source notes for the proposed unit; inspect a fresh complete native target revision and audited source-page coverage; run the canonical overlap preflight. Source gaps, conflicting page maps, unverified hashes, stale revisions, or existing overlapping text **block append**. An already drafted source unit must be reconciled by a bounded revision-guarded amendment, not appended anew.
- **Batch representation:** Supply the exact live Google Docs snapshot, private audited manifest, proposed physical-page unit and a private batch JSON with `tabId`, `entries:[{type:"body"|"heading"|"bullet"|"numbered",text}]` and `notes:[{entryIndex,anchorText,text}]`. Each entry is one logical paragraph; preserve source-to-target structure, sacred quotation formatting, and all original note content. Do not pack a whole book into one transaction. Avoid splitting a paragraph or note across unverified source boundaries.
- **Phase 1 (one revision-guarded native write):** Run `node scripts/prepare-native-draft-batch.mjs /private/live-doc.json /private/manifest.json /private/proposal.json /private/batch.json /private/phase1.json`. Apply only the returned `requests` and `writeControl` through the authorized Google Docs native API. The planner constructs one body insert, native paragraph/list structure first, then explicit **Amiri 14 pt** prose and **18 pt** heading styles, and finally descending-index note anchors. **The order is required**: a synthetic live Docs pilot exposed that applying font size *before* `updateParagraphStyle`/`createParagraphBullets` silently erased the explicit text styles even though the API call succeeded. The corrected request order passed native readback and one-page PDF inspection. This does not yet prove end-to-end book throughput or source fidelity. The tool only plans requests; it does not send them, verify the source, or certify the edition.
- **Phase 2 (one revision-guarded note write):** Supply the confirmed phase-1 native API response and the private phase-1 plan to `node scripts/prepare-native-draft-batch.mjs --populate /private/phase1-response.json /private/phase1.json /private/phase2.json`. Apply the resulting requests so each API-returned footnote ID receives its original source note in **Amiri 10 pt**. Missing/mismatched IDs block the operation. Read the live manuscript back, verify all anchors and complete notes, then render and inspect the same candidate.
- **Note-free optimization:** If the verified logical unit has **zero original footnotes**, phase 1 is the only write; `planPopulateNativeNotes` returns an empty request list with `skipPhase2:true`. Do not send an empty batchUpdate or invent a phase-two revision. The read-only verifier accepts the confirmed phase-one revision as the final revision for such a unit and may be called with four private JSON files plus `tabId`, omitting a phase-two result path. Note-bearing units still require both guarded transactions and all returned note IDs.
- **Phase 3 (read-only native assurance):** After phase 2, fetch the *full* native target snapshot (not only plain extracted text). Run `node scripts/verify-native-draft-batch.mjs /private/final-doc.json /private/batch.json /private/phase1.json /private/phase1-response.json /private/phase2-response.json t.0`. The verifier fail-closes on wrong paragraph text, 1-point/inherited body styles, missing headings/lists, incorrect note attachment positions, missing/wrong note texts and fonts, and stale final revisions. It reports only privacy-safe counts and explicitly leaves Arabic source fidelity, rendered pagination, human approval, and accepted-source-page credit **NOT CHECKED**. Follow with actual rendered-PDF review and independent Arabic clause/note review; do not infer book acceptance from this helper.
- **Failure/quality gates:** The two phases are *not* a transaction: if phase 2 fails, retain phase 1 as a documented incomplete working draft with unfilled native notes, and recover against the exact new revision rather than blind-retry or duplicate append. Independently check clause-level fidelity against rendered Arabic, unapproved Arabic script, all notes/figures, citations, pagination, styles, and the final native TOC. A clean mechanical PDF does not establish scholarly acceptance. Never log private text, IDs, revisions, or source/target JSON to public GitHub; store private plans under restricted, temporary paths and clean them after verified continuity.
- **CI capacity:** `workbench-acceptance.yml` and `workbench-english-target-guard.yml` cancel superseded checks only within the same branch/PR; work on other refs remains separate. Source-image requests are intentionally **not** cancelled because each page range is distinct evidence. This reduces future runner contention but is not evidence that already queued jobs have completed or that any reviewer/source gate can be skipped.
- **Batch-size experiment:** Begin with a source-dense, note-heavy pilot and vary coherent unit size only when the source is available. Measure total **accepted** output, renderer defects, correction/review effort and wall time—not drafted pages or request count alone. Increase lookahead and bundle calls while QA capacity keeps up; revert any setting that accumulates unreviewed debt. No fixed 20-page promise or permission to interleave books.

- **Stay on the parent outcome.** Finish every authorized feasible step rather than stopping after a tracker or repository fix; preserve all blocked/unverified cases with an exact resume action and do not claim the 174-book programme complete before actual source, target, native formatting, reviewer and publication gates are met. Website writes remain deliberately **final-only** as already directed. Report verified throughput improvements, not unsupported claims of being the absolute fastest.

## Preferred division of work

| Work | Preferred host | Boundary |
| --- | --- | --- |
| Book setup, downloads, page mapping, reusable preparation | Windows | Keep Windows OCR/preparation environments, caches, and large working artifacts on D: by default; preserve exact source identity. |
| Arabic OCR and source-text checking | Mac | Use the selected Mac route after source-fidelity checks; OCR only missing or unreliable text. Preserve notes, reading order, diacritics, and punctuation. |
| Translation drafting | Windows | Translate coherent logical paragraphs/notes/cells with book context and terminology, not isolated storage runs. |
| Source-aligned review, formatting, native document/render checks | Mac | Use the capability the artifact requires; macOS-only PDFKit/Vision work stays on Mac. This is not an automatic second translation or deferred second formatting pass. |
| Manuscript writes and Workbench checkpoint publication | One designated writer | The writer owns the exact target revision, readback, and checkpoint; other machines return batch artifacts rather than concurrently editing the final manuscript. |

These are preferred operational roles, conditional on accessible tools and measured performance, not claims that a second Mac is registered or GitHub jobs are already routed. Translation speed depends on the translation engine and its execution location, not RAM or operating-system names alone. CPU-only independent work may overlap. Any Windows GPU-heavy work still follows [GPU scheduling](runner/GPU-SCHEDULING.md) and the exclusive host lock; two runners do not create two GPUs.

## Existing-manuscript migration and destination-account preflight

A request to move a collection of books to a different Google account is **not** authorization to turn already translated or partially translated books into blank targets. Use this gate for migrations and bulk target provisioning in addition to the normal source/translation QA pipeline.

1. Retrieve the **current live** `GET /api/projects` or exact `/api/projects/{id}` records, and establish immutable project ID, exact title/edition, assignment, status, source identity, current English link and page progress. The committed catalogue and historical handoffs are **candidate discovery**, not live Workbench truth. If live access is unavailable, pause production link/start mutations; do not silently proceed from an old manifest.
2. Inventory the authorized account's files **and all known original/historical Docs** before creating a replacement. Search stable project IDs and original/alternate titles; resolve duplicate IDs, wrong editions, shared files, moved docs and prior drafts. Read native content, not just filenames or Drive size, to classify each candidate `nonempty`, `empty`, or `unknown`. A `NOT_FOUND` from one Google identity means **unavailable**, not nonexistent/blank. Record whether that classification is actually verified.
3. For a verified nonempty existing manuscript of the verified exact edition (with no unresolved competing source), choose native Drive **copy existing** and preserve the source. Confirm the copy is owned by the exact destination account, has the intended source lineage, and retains actual content, native notes, styles, headers, tables, lists, links and structure. A matching element count or footnote count is only a structural screening check, **not proof of exact textual/style identity**. If the user said copy exactly as-is, do no translation, editorial corrections or formatting normalization on these copies.
4. Create an **empty new draft** only for a genuinely unstarted book after verified source/destination discovery establishes that no existing translation is being replaced. If any source is inaccessible or source progress is nonzero, leave its proposed target **quarantined/source-recovery**; never call it the manuscript or update the website from it. Bulk permission to establish destinations does not waive this content/identity gate.
5. Before **each** create/copy/link action, run `MIGRATION_APPROVED_OWNER_EMAIL='<privately approved email>' node scripts/manuscript-migration-preflight.mjs /private/migration-inventory.json` against current evidence. The private JSON is a one-project-or-multi-project inventory of `{destinationOwner,rows:[{project:{id,title_en},live:{id,title_en,status,sourcePageProgress,observedThisRun,apiWritable,linkBefore},expectedLinkBefore,inventoryComplete,sourceSearchComplete,sourceCandidates:[{fileId,contentState,contentVerified,editionVerified}],destinationCandidates:[{fileId,kind,ownerEmail,ownerVerified,...}],action,copySourceFileId}]}`. Accepted actions are `copy_existing`, `create_draft`, and `attach_target`; the checker is **read-only**, emits only project IDs/reason codes, and returns nonzero on blocked cases. It cannot fetch Drive metadata or replace independent readback; false caller evidence is not verified by the script.
6. Store the source→destination project/file map, original Google revision, owner, true copy verification, and explicit unresolved access/content exceptions in a **private** destination-account ledger. Don't commit IDs/URLs, book text or credentials into the public repository or paste them into publicly logged Actions. Don't blindly create a second target after a reconnect/error: list Drive and reconcile the previous write outcome first.
7. Only after the destination is fully verified, separately establish Workbench-required `anyone + writer` Drive permission and anonymous access; use the exact live project ID and compare-and-swap its current link. Read back the updated URL and unchanged status, source-page numerators, human-review and publication state before reporting the link changed. If a tool cannot grant public-Editor or the site API is unavailable, **leave the copy private and its website link unchanged**. Never downgrade the live site's access requirements or fabricate permission evidence to bypass the gate.
8. For a verified empty superseded placeholder, quarantine/rename and retain it until the live site has been checked for references; only then consider deletion under the appropriate authorization and recovery controls. Distinguish created/copied/preserved vs exact-fidelity-verified vs link-synchronized vs translation-complete in every portfolio report.
